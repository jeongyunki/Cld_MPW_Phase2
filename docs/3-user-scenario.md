# MPW Plus 2차 개발 사용자 시나리오 (User Scenario)

> 작성 단계: 사용자 시나리오 (3/6) — 이전 단계는 도메인정의서 → PRD → (현 문서) → 다음 단계는 페르소나 정의 → ERD 설계 → 실행계획 → UI 설계 순으로 진행한다.
> 이 문서는 PRD 2절의 3개 "대표 사용 시나리오"를 구체적인 단계별 사용자 여정(user journey)으로 풀어써서, 다음 단계 작업자가 "실제로 화면에서 어떤 순서로 무슨 일이 벌어지는지"를 명확히 이해할 수 있도록 한다. 이 단계에서는 아직 화면 UI(버튼 위치, 레이아웃)을 설계하는 것이 아니라, "누가, 어떤 상황에서, 무엇을 하려고, 어떤 순서로 시스템과 상호작용하고, 결과가 무엇인지"에 집중한다.

---

## 1. 개요

### 문서의 목적

도메인정의서와 PRD에 정의된 기능과 사용자 세그먼트를 바탕으로, 실제 업무 흐름 속에서 사용자들이 MPW Plus와 상호작용하는 구체적인 단계를 기술한다. 이를 통해:
- 페르소나 정의 작업자: 각 세그먼트별 사용 목표와 동기를 명확히 파악
- ERD/실행계획 작업자: 데이터 흐름과 API 요청 순서를 예상
- UI 설계 작업자: 화면 전환 순서와 사용자 입력 흐름을 파악

### PRD와의 관계

PRD 2절의 3개 대표 사용 시나리오를 다음과 같이 확장한다:
- "MapGen 도면 작성" → **시나리오 1**: Deliverables 등록 → MapGen 도면 생성 (여정 5단계)
- "임가공 진행 관리" → **시나리오 2**: 임가공 계획 등록부터 의뢰 확정까지 (여정 7단계, 여러 날에 걸침)
- "Master 항목 유지보수" → **시나리오 3**: Master Page 항목 추가 및 실시간 반영 (여정 3단계)
- **추가 시나리오 4**: 동시 편집 상황과 충돌 처리

### 시나리오 표기법

각 시나리오는 다음 요소를 포함한다:
- **시작 조건**: 언제/왜 이 일이 발생하는가
- **등장인물**: 어떤 사용자 세그먼트가 참여하는가
- **단계별 절차**: 시스템과의 상호작용을 번호로 표시
- **정상 종료 결과**: 프로세스가 정상 완료되었을 때 상태
- **관련 FR 번호**: PRD의 기능 요구사항 매핑

예외/오류 시나리오는 각 메인 시나리오 후에 **[예외]** 표시로 구분한다.

## 2. 시나리오 1: Deliverables 등록 → MapGen 도면 생성

### 시작 조건 및 배경
- MPW 칩 설계가 완료되어, 새로운 차수(예: "MPW 2026-Q3")에 대한 공정명(예: "0.13um")의 엑셀 데이터가 기획팀에 준비되었다.
- 설계팀이 칩 도면을 생성하기 위해 파일을 필요로 한다.
- 지금까지는 개인 이메일이나 USB로 엑셀을 전달했으나, 이제 MPW Plus의 Deliverables Page를 통해 중앙 집중식으로 관리한다.

### 등장인물
- **기획팀** (Deliverables 등록자)
- **설계팀** (도면 생성자)
- **품질팀 / 제조팀** (도면 참고자)

### 단계별 여정

#### 기획팀의 역할

1. **기획팀 담당자가 MPW Plus에 로그인하고 Deliverables Page 접속**
   - 좌측 메뉴에서 "Deliverables" 클릭 → 페이지 로드
   - 현재 등록된 Deliverables 목록이 표 형태로 표시 (차수, 공정명, 파일명, 등록일시, 등록자)
   - **관련 FR**: FR-DL-02 (Deliverables 목록 조회)

2. **Create 버튼 클릭하여 등록 팝업 오픈**
   - 팝업에 "차수", "공정명", "파일 선택" 입력 필드 표시
   - 예시 문구: "새로운 Deliverables를 등록하려면 차수와 공정명을 입력한 뒤 엑셀 파일을 선택하세요"

3. **팝업에서 차수/공정명 입력 및 엑셀 파일 선택**
   - 텍스트 입력: 차수 = "MPW 2026-Q3", 공정명 = "0.13um"
   - 파일 선택: 로컬 디스크의 엑셀 파일 (예: `chip_design_0.13um.xlsx`) 선택
   - 파일 크기 확인: 10MB 이상이면 경고 메시지 표시 (예시 문구: "파일이 10MB를 초과합니다")
   - **관련 FR**: FR-DL-01 (Deliverables 등록)

4. **"등록" 버튼 클릭**
   - 프론트엔드가 `POST /api/deliverables`로 요청 전송 (multipart/form-data)
   - 백엔드가 파일을 서버에 저장하고 DB에 메타데이터 기록 (차수, 공정명, 파일경로, 등록일시, 등록자)
   - 팝업이 닫히고 목록 테이블에 새 행이 즉시 추가됨 (상단 또는 "최신순" 정렬 기준)

5. **기획팀이 목록에서 새 항목 확인**
   - 테이블에 "MPW 2026-Q3 | 0.13um | chip_design_0.13um.xlsx | 2026-09-28 14:30 | 기획팀_담당자" 행 표시
   - 등록 완료 (기획팀 역할 종료)
   - **관련 FR**: FR-DL-02 (등록 후 목록 반영)

#### 설계팀의 역할

6. **설계팀 담당자가 MPW Plus에 로그인하고 MapGen Web 페이지 접속**
   - 좌측 메뉴에서 "MapGen Web" 클릭
   - 기존 입력 방식(엑셀 붙여넣기) 이외에 새로운 "Excel 파일 선택" 버튼 표시
   - **관련 FR**: FR-MG-02 신규 기능 화면 진입

7. **"Excel 파일 선택" 버튼 클릭**
   - 팝업이 열려 Deliverables 목록 테이블이 표시 (차수, 공정명, 등록일시 컬럼)
   - 위에서 기획팀이 등록한 "MPW 2026-Q3 | 0.13um | 2026-09-28 14:30" 행이 보임
   - **관련 FR**: FR-DL-02 (MapGen 팝업 내에서도 조회)

8. **팝업에서 해당 행(차수+공정명) 선택**
   - 설계팀 담당자가 "MPW 2026-Q3" 행을 클릭
   - 팝업이 닫히고 백엔드에서 해당 엑셀 파일(`chip_design_0.13um.xlsx`) 다운로드 시작
   - **관련 FR**: FR-MG-02 (파일 선택), FR-DL-03 (파일 다운로드)

9. **MapGen의 파싱 로직이 자동 실행**
   - 다운로드한 엑셀을 메모리에 로드
   - 기존의 텍스트 파싱 로직(`parseModuleData.js`)이 자동 실행
   - textarea에 파싱된 데이터가 자동 입력됨 (사용자는 붙여넣기 할 필요 없음)
   - 엑셀 첫 번째 시트에 붙어 있는 칩 이미지가 "2) 참조 이미지 & 결과" 영역의 이미지로 자동 표시됨 (이미지가 없으면 예외 1-6)
   - **관련 FR**: FR-MG-02 (자동 입력)

10. **canvas에 도면이 자동으로 그려짐**
    - Module 사각형, Sawing Line, 치수 화살표가 칩 이미지 위에 표시됨
    - 설계팀이 도면을 확인하고 필요시 저장 또는 출력
    - **관련 FR**: 기존 FR-MG-01 (파싱 및 도형 렌더링)

#### 품질팀 / 제조팀의 역할

11. **품질팀이 MapGen Web 페이지 접속하여 도면 조회**
    - 위 단계 1~10을 반복하여 같은 도면을 볼 수 있음
    - 도면을 참고하여 모듈 검증 수행
    - **관련 FR**: FR-MG-02 (재사용 가능성)

12. **제조팀이 MapGen Web 페이지 접속하여 Sawing 작업 수행**
    - 도면의 Sawing Line을 참고하여 웨이퍼 절단 작업 진행
    - **관련 FR**: FR-MG-02 (제조팀 사용)

### 정상 종료 상태
- ✅ Deliverables Page에 "MPW 2026-Q3 | 0.13um" 항목이 등록되어 있음
- ✅ MapGen Web에서 파일을 선택하면 즉시 도면이 생성됨
- ✅ 설계팀/품질팀/제조팀이 동일한 도면을 중앙에서 참고 가능

### 관련 기능 요구사항
- FR-DL-01: Deliverables 등록 (기획팀)
- FR-DL-02: Deliverables 목록 조회 (모든 사용자)
- FR-DL-03: Deliverables 파일 다운로드 (설계팀)
- FR-MG-02: Deliverables 파일 선택 입력 (설계팀, 품질팀, 제조팀)
- FR-MG-01: 기존 엑셀 텍스트 붙여넣기 입력 (유지)

### [예외 시나리오 1-1] 필수값 미입력

**상황**: 기획팀이 차수는 입력했지만 공정명 필드를 비워둔 채 "등록" 버튼을 클릭

**절차**
1. 팝업의 "등록" 버튼 클릭
2. 프론트엔드가 필수값 검사 실패 → 에러 메시지 표시
3. 예시 문구: "공정명은 필수입니다" (또는 "필수 입력값을 확인하세요")
4. 팝업은 열린 상태로 유지, 사용자가 공정명 입력 후 재시도

**결과**: 등록 실패, 사용자는 입력값을 수정하고 재시도해야 함

**관련 수용기준**: FR-DL-01 "차수/공정명 미입력 시 필수 입력값 에러 표시"

---

### [예외 시나리오 1-2] 파일 크기 초과

**상황**: 기획팀이 50MB 용량의 엑셀 파일을 선택하여 등록하려 함

**절차**
1. 차수, 공정명 입력
2. 50MB 파일 선택
3. "등록" 버튼 클릭
4. 프론트엔드가 파일 크기 확인 (10MB 제한)
5. 경고 메시지 표시
6. 예시 문구: "파일 크기가 10MB를 초과합니다. 파일을 줄이거나 다른 방식으로 제공하세요"
7. 등록 취소, 팝업 열린 상태 유지

**결과**: 등록 실패, 기획팀은 파일을 압축하거나 분할 후 재시도

**관련 수용기준**: FR-DL-01 "파일 크기 제한"

---

### [예외 시나리오 1-3] 동일 차수+공정명의 중복 등록

**상황**: 기획팀이 이미 등록되어 있는 "MPW 2026-Q3 | 0.13um"을 다시 등록하려 함 (파일만 다름)

**절차**
1. 차수 = "MPW 2026-Q3", 공정명 = "0.13um" 입력
2. 다른 엑셀 파일(`chip_design_0.13um_v2.xlsx`) 선택
3. "등록" 버튼 클릭
4. 백엔드가 동일 차수+공정명 확인
5. 두 가지 처리 옵션 (다음 단계에서 결정):
   - **옵션 A**: "동일한 차수+공정명이 이미 있습니다" 경고 후 진행 여부 재확인
   - **옵션 B**: 그냥 허용하고 목록에 중복 표시 (FR-DL-02 수용기준 "중복 허용")
6. 현 단계에서는 **옵션 B 가정** — 목록에 두 행이 모두 표시됨 (최신순 정렬)

**결과**: 등록 성공, 목록에 "MPW 2026-Q3 | 0.13um | chip_design_0.13um_v2.xlsx | 2026-09-28 15:00" 행 추가

**관련 수용기준**: FR-DL-02 "같은 차수+공정명이 여러 번 등록된 경우 모두 표시"

---

### [예외 시나리오 1-4] MapGen 파일 선택 시 파일 다운로드 실패

**상황**: 설계팀이 MapGen에서 "Excel 파일 선택" 팝업을 열어 행을 선택했지만, 네트워크 오류로 파일 다운로드 실패

**절차**
1. 설계팀이 팝업에서 행 선택
2. 백엔드에서 파일 다운로드 시도
3. 네트워크 오류 발생 (또는 파일이 서버에서 삭제된 경우)
4. 에러 메시지 표시
5. 예시 문구: "파일을 불러올 수 없습니다. 나중에 다시 시도하세요"
6. 팝업은 닫히고 MapGen의 textarea는 비어있는 상태 유지

**결과**: 도면 생성 실패, 설계팀은 재시도하거나 기획팀에 문의

**관련 수용기준**: FR-MG-02 "파일 선택 실패 시 에러 메시지 표시"

---

### [예외 시나리오 1-5] 기존 데이터 덮어쓰기 확인

**상황**: 설계팀의 MapGen textarea에 이미 다른 엑셀 데이터가 입력되어 있는데, "파일 선택" 버튼으로 새 파일을 선택하려 함

**절차**
1. textarea에 기존 데이터 있음
2. 설계팀이 "파일 선택" 버튼 클릭 → 팝업 오픈
3. 팝업에서 행 선택
4. 확인 팝업 표시
5. 예시 문구: "기존 데이터를 덮어쓰시겠습니까?"
6. 확인 버튼 클릭 시 새 파일 데이터 로드, 취소 시 기존 데이터 유지

**결과**: 사용자가 선택한 대로 처리됨

**관련 수용기준**: FR-MG-02 "textarea가 이미 데이터를 담고 있으면 확인 후 진행"

---

### [예외 시나리오 1-6] 선택한 엑셀에 칩 이미지가 없음

**상황**: 설계팀이 팝업에서 행을 선택했지만, 그 엑셀 파일의 첫 번째 시트에 칩 이미지가 붙어 있지 않음

**절차**
1. 설계팀이 팝업에서 행 선택 → 파일 다운로드 성공
2. textarea에는 셀 데이터가 정상 입력되고 module 표도 갱신됨
3. 참조 이미지 영역에는 이전 이미지 대신 경고 표시
4. 예시 문구: "image가 없으니 excel 파일을 다시 확인하세요."
5. 설계팀이 이미지를 직접 선택하거나, 이미지가 있는 엑셀을 다시 선택하면 경고가 사라지고 도면이 그려짐

**결과**: 이미지 없이 다른 파일의 이미지 위에 도면이 그려지는 혼동을 막고, 기획팀에 이미지가 포함된 파일로 다시 등록하도록 요청할 수 있음

**관련 수용기준**: FR-MG-02 "첫 번째 시트에 이미지가 없으면 참조 이미지 영역에 경고 표시"

## 3. 시나리오 2: 임가공 계획 등록 → 취합 → 의뢰 확정 → 진행상태 관리

### 시작 조건 및 배경
- 회사의 임가공(외주 조립·가공) 업무가 매달 반복된다.
- 그동안 설계팀의 여러 담당자가 개인 엑셀로 임가공 항목을 따로 관리했다.
- 이제 MPW Plus의 임가공 Plan 페이지에서 중앙 집중식으로 관리하고, MPW 관리자가 월말에 일괄 확정한다.
- 이 시나리오는 **여러 날에 걸쳐** 진행되는 월간 업무 사이클을 다룬다.

### 등장인물
- **설계팀** (임가공 항목 신청자, 여러 명의 담당자)
- **MPW 관리자** (월별 취합 및 의뢰 확정자)

### 단계별 여정

#### 첫째 주 - 설계팀의 개별 항목 신청 (여러 날에 걸침)

1. **설계팀 담당자 A가 임가공 Plan 페이지 접속**
   - 좌측 메뉴에서 "임가공 Plan" 클릭
   - 현재 등록된 임가공 행들이 테이블로 표시 (Date, Status, 구분, 조립처, ... 등 13개 컬럼)
   - **관련 FR**: FR-IM-02 (임가공 목록 조회)

2. **새로운 임가공 항목 신청을 위해 "Add Row" 팝업 오픈**
   - 예시 문구: "새로운 임가공 항목을 신청하려면 아래 정보를 입력하세요"
   - 팝업의 입력 필드:
     - dropdown: 구분, 조립처, Chip size, PKG Type
     - key-in: Module, 과제명, GCM Code, 고객, LOT수, PKG 수량, 과제 담당자
   - **관련 FR**: FR-IM-01 (임가공 행 추가)

3. **담당자 A가 팝업에서 정보 입력**
   - 예시 입력값:
     - 구분: "조립비"
     - 조립처: "Amkor (광주)"
     - Chip size: "8인치"
     - PKG Type: "p-type1"
     - Module: "Module-A"
     - 과제명: "AI Chip v2"
     - GCM Code: "GCM-2026-001"
     - 고객: "고객사 X"
     - LOT수: 10
     - PKG 수량: 100
     - 과제 담당자: "담당자A"
   - **관련 FR**: FR-IM-01 (필수값 확인)

4. **"저장" 버튼 클릭**
   - 프론트엔드가 `POST /api/imgagong-plans`로 요청
   - 백엔드가 새 행을 DB에 저장
   - 자동으로 생성일시(date) = "2026-09-21 09:30" (현재 시각), status = 'new' 입력
   - 팝업이 닫히고, 테이블에 새 행이 즉시 표시됨
   - **관련 FR**: FR-IM-01 (저장 및 목록 반영)

5. **같은 시간에 설계팀 담당자 B도 항목 신청**
   - 담당자 B가 같은 페이지에 접속하면 담당자 A가 방금 추가한 행이 **실시간으로 나타남**
   - 담당자 B도 자신의 항목을 추가 (예: Module-B, 과제명 "Power Chip")
   - 테이블에 담당자 B의 새 행도 즉시 추가
   - **관련 FR**: FR-IM-05 (실시간 공유)

6. **넷째 주가 되고, 여러 설계 담당자가 항목을 추가함**
   - 테이블에는 지난 2주간 등록된 여러 개의 임가공 행이 쌓여있음
   - 각 행의 Status는 모두 'new' 상태
   - Date 기준으로 최신순 정렬 (기본값)

#### 월말 - MPW 관리자의 취합 및 의뢰 확정

7. **MPW 관리자가 임가공 Plan 페이지 접속 (월말, 예: 9월 30일)**
   - 같은 임가공 Plan 페이지 접속
   - Status가 'new'인 모든 행들을 확인
   - 기간 필터: 시작월 = "2026-09", 종료월 = "2026-09" 선택 (또는 기본값이 현월일 수도 있음)
   - 필터 적용 후 9월에 등록된 모든 항목이 표시됨
   - **관련 FR**: FR-IM-02 (기간 필터)

8. **MPW 관리자가 의뢰할 항목들을 체크박스로 선택**
   - 테이블 좌측의 체크박스로 여러 행 선택 (예: 15개 항목)
   - 예시 문구: "선택됨: 15개 항목"
   - **관련 FR**: FR-IM-06 (일괄 선택)

9. **"의뢰 확정" 버튼 클릭**
   - 확인 팝업 표시
   - 예시 문구: "선택된 15개 항목을 의뢰 확정하시겠습니까?"
   - **관련 FR**: FR-IM-06 (확인 팝업)

10. **확인 팝업에서 "확정" 버튼 클릭**
    - 프론트엔드가 `PATCH /api/imgagong-plans` (또는 별도 엔드포인트) 호출
    - 선택된 15개 행의 Status를 일괄로 변경 (예: 'new' → 'requested' 또는 'confirmed')
    - **관련 FR**: FR-IM-06 (상태 일괄 변경)

11. **변경 사항이 **실시간으로 전체 사용자에게 반영됨**
    - 같은 페이지를 보고 있는 설계팀 담당자 C의 화면에도 즉시 반영됨
    - 예: Status 컬럼이 'new'에서 'requested'로 변경됨
    - 예시 문구: "의뢰가 확정되었습니다" (toast 알림 등)
    - **관련 FR**: FR-IM-05 (실시간 공유), FR-IM-06 (결과 반영)

#### 의뢰 후 진행 상황 관리 (10월)

12. **10월 1일, MPW 관리자가 진행 상황을 조회하려 함**
    - 기간 필터: 시작월 = "2026-09", 종료월 = "2026-09" (지난달 항목들)
    - 필터 적용 후 9월에 의뢰된 15개 항목 조회 가능
    - **관련 FR**: FR-IM-02 (월별 조회)

13. **의뢰 이후 각 항목의 상태 업데이트**
    - 조립처에서 칩이 도착하고 진행 상황이 변함
    - MPW 관리자 또는 현장 담당자가 각 행의 Status를 업데이트
    - 예: 1번 행의 Status를 'requested' → 'in-progress' (진행 중)
    - 다른 사용자의 화면에 실시간 반영
    - **관련 FR**: FR-IM-03 (행 편집), FR-IM-05 (실시간 공유)

14. **모든 항목이 완료되면 최종 상태로 업데이트**
    - 각 항목의 Status를 최종 상태로 변경 (예: 'completed')
    - MPW 관리자가 진행 현황 조회 → 모든 항목이 완료됨을 확인
    - **관련 FR**: FR-IM-03 (상태 업데이트)

### 정상 종료 상태
- ✅ 설계팀이 입력한 모든 임가공 항목이 중앙의 한 화면에서 관리됨
- ✅ MPW 관리자가 월별로 항목을 조회하고 일괄 의뢰 확정 가능
- ✅ 의뢰 이후 진행 상황을 지속적으로 추적 가능
- ✅ 모든 변경 사항이 실시간으로 전체 사용자에게 공유됨

### 관련 기능 요구사항
- FR-IM-01: 임가공 행 추가 (설계팀)
- FR-IM-02: 임가공 목록 조회 및 기간 필터 (MPW 관리자)
- FR-IM-03: 행 편집 (Status, 기타 필드 업데이트)
- FR-IM-05: 실시간 공유 (모든 사용자)
- FR-IM-06: 의뢰 일괄 확정 (MPW 관리자)

### [예외 시나리오 2-2] 동시 편집 충돌 - 낙관적 잠금 발동

**상황**: MPW 관리자와 설계팀 담당자가 동시에 같은 임가공 행을 편집

**절차**
1. 설계팀 담당자 A가 테이블에서 1번 행의 "과제명" 필드를 클릭하여 "AI Chip v2"에서 "AI Chip v2.1"로 변경
2. 동시에 MPW 관리자가 같은 1번 행의 Status를 'new'에서 'checked'로 변경
3. 담당자 A가 먼저 저장 (PATCH 요청 전송, 현재 버전 = 1)
4. 백엔드가 버전 1 상태에서의 변경을 저장하고, 행의 버전을 2로 증가
5. 다음으로 MPW 관리자가 저장 시도 (PATCH 요청, 버전 = 1 — 이미 변경되었음)
6. 백엔드가 버전 불일치 감지
7. 에러 응답 반환
8. 프론트엔드가 에러 팝업 표시
9. 예시 문구: "다른 사용자가 먼저 이 행을 수정했습니다. 페이지를 새로고침한 후 다시 시도하세요"
10. MPW 관리자가 "새로고침" 버튼 클릭 → 최신 데이터 로드
11. 최신 데이터에는 담당자 A의 변경사항(과제명 = "AI Chip v2.1")이 반영되어 있음
12. MPW 관리자가 Status 변경을 다시 시도

**결과**: 데이터 손상 없이, 마지막 쓰기 방식이 아닌 버전 기반으로 충돌 감지 및 해결

**관련 수용기준**: FR-IM-05 "데이터 충돌 처리: 낙관적 잠금 구현", 비기능 요구사항 4.2절 "낙관적 잠금"

## 4. 시나리오 3: Master Page 항목 관리

### 시작 조건 및 배경
- MPW 관리자가 조립처 목록에 새로운 외주업체를 추가하려 함
- 이 변경 사항이 즉시 전체 사용자의 dropdown에 반영되어야 함
- 현재 구분/조립처/PKG Type 등 dropdown 옵션들은 Master Page에서 중앙 관리됨

### 등장인물
- **MPW 관리자** (Master Page 수정자)
- **설계팀 / 기타 사용자** (변경사항 실시간 반영 수신자)

### 단계별 여정

1. **MPW 관리자가 Master Page 접속**
   - 좌측 메뉴에서 "Master" 클릭
   - 현재 등록된 dropdown 항목들이 필드별로 표시 (Status, 구분, 조립처, Chip size, PKG Type)
   - 각 필드마다 별도 섹션으로 표시됨 (예: "조립처" 섹션에 현재 항목 목록)
   - **관련 FR**: FR-MS-02 (Master 항목 조회)

2. **조립처 섹션에서 "Add Item" 버튼 클릭**
   - 팝업 또는 인라인 입력 필드 표시
   - 예시 문구: "새로운 조립처 이름을 입력하세요"
   - **관련 FR**: FR-MS-01 (Master 항목 추가)

3. **새로운 조립처명 입력**
   - 예시 입력: "삼성전자 평택"
   - **관련 FR**: FR-MS-01 (항목명 입력)

4. **"저장" 또는 "추가" 버튼 클릭**
   - 프론트엔드가 `POST /api/master-items` 요청 전송 (필드명 = "조립처", 항목명 = "삼성전자 평택")
   - 백엔드가 새 항목을 DB에 저장
   - 팝업이 닫히고, Master Page의 조립처 목록에 새 항목 표시됨 (가장 아래 또는 정렬된 위치)
   - **관련 FR**: FR-MS-01 (저장 및 목록 반영)

5. **동시에 다른 사용자들의 임가공 Plan 화면이 **실시간으로 업데이트됨**
   - 설계팀 담당자가 임가공 Plan 페이지를 보고 있는 중
   - "Add Row" 팝업의 "조립처" dropdown에 새로운 "삼성전자 평택" 항목이 즉시 나타남
   - **관련 FR**: FR-MS-01 (다른 사용자의 dropdown에 즉시 반영)

6. **설계팀 담당자가 새로운 조립처를 선택하여 임가공 행 생성**
   - Add Row 팝업의 조립처 dropdown에서 "삼성전자 평택" 선택 가능
   - 항목을 선택하고 저장하면, 테이블에 "조립처 = 삼성전자 평택"인 행이 추가됨
   - **관련 FR**: 기존 FR-IM-01과 FR-MS-01의 연계

### 정상 종료 상태
- ✅ Master Page에 "삼성전자 평택" 항목이 조립처 목록에 추가됨
- ✅ 전체 사용자의 임가공 Plan, Deliverables Page 등에서 이 항목을 dropdown으로 선택 가능

## 5. 시나리오 4: 여러 사용자의 동시 편집 및 실시간 공유

### 시작 조건 및 배경
- 임가공 Plan 페이지는 1000명 규모의 조직에서 동시에 50~100명이 접속하는 상황을 상정함 (PRD 1절, 비기능 요구사항)
- 대부분의 사용자는 조회만 하지만, 일부는 동시에 입력/편집함
- 이 시나리오는 "일상적인 사내 도구의 동시 접속 상황"을 다룬다

### 등장인물
- **설계팀 담당자** (여러 명, 동시 접속)
- **MPW 관리자** (동시 조회)
- **기술팀** (참고용 조회)

### 단계별 여정

1. **아침 9시, 회의가 끝나고 여러 설계팀 담당자가 임가공 Plan 페이지 동시 접속**
   - 담당자 A, B, C, D 등이 동시에 페이지를 열음
   - 각 사용자의 화면에 같은 데이터가 로드됨 (지난달까지의 임가공 행들)
   - **관련 FR**: FR-IM-02 (동시 조회 시 일관된 데이터)

2. **담당자 A가 "Add Row" 팝업에서 새로운 항목 입력 및 저장**
   - 여정 2 시나리오의 단계 2~4와 동일
   - 저장 완료
   - **관련 FR**: FR-IM-01 (항목 추가), FR-IM-05 (실시간 공유)

3. **즉시 담당자 B, C, D의 화면에도 새 행이 나타남**
   - 백엔드가 실시간 알림 브로드캐스트 (SSE 또는 WebSocket)
   - 4명 모두의 화면에서 테이블이 자동 업데이트됨 (스크롤 위치 유지, 기존 편집 상태 보존)
   - **관련 FR**: FR-IM-05 (모든 클라이언트에 실시간 반영)

4. **MPW 관리자가 같은 페이지를 접속**
   - 이미 등록된 모든 항목이 표시됨 (담당자 A~D의 항목 포함)
   - 기간 필터를 "현월"로 설정

5. **담당자 A와 B가 동시에 같은 행을 편집**
   - 담당자 A: 1번 행의 "과제명"을 "AI Chip v2"에서 "AI Chip v2.1"로 변경, 저장
   - 동시에 담당자 B: 같은 1번 행의 "LOT수"를 "10"에서 "20"으로 변경, 저장 시도
   - 낙관적 잠금 충돌 발생 (시나리오 2의 예외 2-2 참조)
   - 담당자 B의 요청이 실패 → 에러 메시지 표시
   - 담당자 B가 새로고침 후 재시도
   - **관련 FR**: FR-IM-05 (실시간 공유), 비기능 요구사항 4.2절 (동시성 제어)

6. **담당자 C가 3번 행의 조립처 dropdown을 변경**
   - dropdown을 클릭하면 Master Page에서 방금 추가된 "삼성전자 평택" 항목이 보임
   - 이를 선택하고 저장
   - **관련 FR**: Master Page의 실시간 공유와 연계

7. **기술팀이 참고용으로 임가공 Plan을 조회**
   - "기간 필터"를 "현월"로 설정하고 조회
   - 지금까지 설계팀이 입력한 모든 항목 (A, B, C, D의 항목 + 담당자 B의 재시도 후 최종 상태)이 표시됨
   - 기술팀은 이를 참고만 하고 편집은 하지 않음

8. **오후 5시 54분, MPW 관리자가 마지막 확인**
   - 기간 필터를 "현월"로 설정하고, 모든 항목이 준비됨을 확인
   - 체크박스로 여러 행 선택
   - "의뢰 확정" 버튼 클릭
   - 앞의 시나리오 2의 단계 9~11과 동일하게 진행

9. **모든 사용자의 화면이 실시간 업데이트**
   - 설계팀 담당자들의 화면에 상태 변경 반영
   - 기술팀의 화면에도 반영
   - **관련 FR**: FR-IM-05 (모든 변경사항 실시간 공유)

### 정상 종료 상태
- ✅ 50~100명의 동시 접속자 중 대부분이 조회, 일부가 입력/편집할 때 충돌 없이 진행
- ✅ 각 사용자의 화면이 실시간으로 동기화됨
- ✅ 응답 시간 2초 이내 유지 (비기능 요구사항 4.1절)
- ✅ 낙관적 잠금으로 데이터 충돌 감지 및 해결

### 관련 기능 요구사항
- FR-IM-01: 항목 추가 (동시 다중 사용자)
- FR-IM-02: 목록 조회 (동시 다중 사용자)
- FR-IM-03: 행 편집 (동시 다중 사용자)
- FR-IM-05: 실시간 공유 (모든 사용자에게 변경사항 즉시 반영)
- FR-IM-06: 의뢰 일괄 확정 (MPW 관리자, 모든 사용자에게 반영)
- 비기능 요구사항 4.1절: 응답 시간 < 2초
- 비기능 요구사항 4.2절: 낙관적 잠금

## 6. 경계 밖 시나리오 (Out-of-Scope 명확화)

- 예시 안내 문구: "의뢰 확정 후, 필요한 경우 사내 결재 시스템에서 별도로 품의하세요"

**Out-of-Scope 처리**

- 예시 안내 문구: "의뢰 확정 후, 조립처 연락처를 통해 별도로 비용을 협상하세요"
- **관련 명세**: 도메인정의서 2절, PRD 6절 Out-of-scope

### Assembly Workflow와 임가공 Plan의 연동 제외

**시나리오**: 임가공 의뢰 확정 시, 1차 시스템의 Assembly Workflow 상태가 자동으로 업데이트되기를 기대

**Out-of-Scope 처리**
- 임가공 Plan과 Assembly Workflow는 **독립적인 두 개의 기능**
- Assembly Workflow: 특정 MPW 차수의 module을 조립할지 여부를 결정하고 진행 상태를 관리 (1차 시스템의 기존 기능)
- 임가공 Plan: 매월 반복되는 외주 조립·가공 업무를 관리하는 별개의 현황 추적 도구 (2차 신규 기능)
- 두 시스템 간 자동 동기화 없음
- 예시 안내 문구: "Assembly Workflow와 임가공 Plan은 별개 시스템입니다. 필요시 담당자가 수동으로 정보를 연계하세요"
- **관련 명세**: 도메인정의서 5절 "임가공은 Assembly Workflow와 독립적"

---

### 1차 시스템의 Deliverables 실제 데이터 통합 제외

**시나리오**: 2차 프로토타입의 Deliverables Page에 등록된 파일과, 1차 시스템에 이미 있는 Deliverables 데이터를 통합하려 함

**Out-of-Scope 처리**
- 이 저장소는 1차 시스템의 실제 데이터에 접근할 수 없음 (아키텍처상 별도 코드베이스)
- 2차 개발이 완료되어 1차 개발자에게 코드를 전달하고 병합될 때, **1차 시스템과의 데이터 통합은 별도 과제로 처리**
- 현재 Deliverables Page는 2차 프로토타입 전용 독립 구현
- 예시 안내 문구: "현재는 프로토타입이므로 1차 시스템의 Deliverables와 별개입니다. 병합 후 별도로 데이터 마이그레이션을 진행하세요"
- **관련 명세**: 도메인정의서 3절, 8절 미해결 사항, PRD 7절 Out-of-scope

---

### 모바일 앱 제외

**시나리오**: 사용자가 스마트폰에서 임가공 Plan이나 MapGen을 접근하려 함

**Out-of-Scope 처리**
- MPW Plus는 웹 기반 시스템이며, 모바일 앱은 제공하지 않음
- 모바일 브라우저에서 웹 페이지를 열 수는 있지만, UI/UX가 모바일에 최적화되지 않음
- 예시 안내 문구: "MPW Plus는 데스크톱 환경에 최적화되어 있습니다. 스마트폰에서 접근할 수 있지만, 화면이 작아 사용성이 낮을 수 있습니다"
- **관련 명세**: PRD 4.5절 "모바일 브라우저는 미지원", 7절 Out-of-scope

---

### 다국어 지원 제외

**시나리오**: 해외 지사의 사용자가 영어나 중국어로 시스템을 사용하려 함

**Out-of-Scope 처리**
- MPW Plus는 한국어 기본 언어로 제공
- 다국어 지원은 2차 개발 범위에 포함되지 않음
- 예시 안내 문구: "현재는 한국어로만 제공됩니다. 향후 필요시 다국어 지원을 검토하겠습니다"
- **관련 명세**: PRD 7절 Out-of-scope

## 7. 다음 단계로 넘기는 사항

### 페르소나 정의 단계에서 다룰 사항

1. **각 사용자 세그먼트의 구체적 페르소나**
   - PRD 2절의 6개 세그먼트(기획팀, 설계팀, 기술팀, 제조팀, 품질팀, MPW 관리자)를 더 세분화
   - 예: "기획팀" → "기획팀 내에서 Deliverables 등록을 담당하는 담당자" vs "기획팀 내에서 MapGen 도면만 참고하는 담당자"
   - 각 페르소나의 목표, 통증점, 사용 빈도 정의

2. **세그먼트별 사용 패턴**
   - MapGen: 설계팀은 주 1~2회 사용, 품질팀은 월 1회 참고
   - 임가공 Plan: 설계팀은 매일 확인하되 월말에 집중적 입력, MPW 관리자는 월말 1~2시간 집중 사용
   - Master Page: MPW 관리자는 월 1~2회 유지보수
   - 각 페르소나별 세션 길이, 피크 타임 예상

3. **Master Page 접근 권한의 구체적 정의**
   - "MPW 관리자"가 실제로 몇 명이고, 어떤 조직 구조 내에 있는지 (예: "생산 총괄 과장 1명" vs "각 사업부별 담당자 5~10명")
   - 이에 따라 인증 시스템의 역할 정의 필요

### ERD 설계 단계에서 다룰 사항

1. **정확한 테이블 스키마**
   - 시나리오에서 다룬 각 엔티티의 필드 명시 (예: imgagong_plan 테이블의 "version" 컬럼, "created_at", "updated_at" 타입과 제약)
   - 각 필드의 NULL 허용 여부, 기본값

2. **권한 테이블 구조 (RBAC)**
   - User-Role 관계
   - Role-Permission 관계
   - 시나리오에서 다룬 삭제 권한, Master Page 접근 권한의 구체적 구현 방식

3. **파일 메타데이터 테이블**
   - Deliverables 파일의 메타데이터 저장 형식 (파일명, 크기, 저장 경로, 업로드자, 체크섬 등)

4. **감시/감사 로그 테이블 (선택사항)**
   - 장기적으로 필요한 경우를 대비한 스키마 설계 (예: created_at, updated_at, last_updated_by)
   - 시나리오 2에서 "마지막 수정일시"와 "수정자" 기록 언급 — ERD 단계에서 구현 여부 최종 결정

5. **인덱싱 전략**
   - 기간 필터 기반 조회 성능을 위해 date 컬럼에 인덱스 필요
   - 차수/공정명 검색을 위한 인덱스 설계

### 실행계획 단계에서 다룰 사항

1. **구체적 API 엔드포인트 상세 정의**
   - 요청/응답 스키마 정의 (예: POST /api/imgagong-plans의 요청 바디)
   - 페이지네이션 구현 방식 (offset/limit vs cursor)
   - 필터링 쿼리 문법

2. **1차 시스템과의 인증 통합 방식 최종 확정**
   - 도메인정의서 8절, PRD 5절에서 "권장안"으로 제시했던 "1차 사용자/권한 기반 활용" 방식이 실제로 구현 가능한지 1차 개발자와 협의
   - 불가능 시 폴백안(자체 구현) 선택

3. **데이터 충돌 처리 구현 세부사항**
   - 낙관적 잠금 구현: 버전 번호 증가 로직, 충돌 감지 시 응답 형식
   - 클라이언트 측 재시도 로직 상세화

4. **백업 및 재해복구 전략**
   - 데이터베이스 백업 정책 (일일 자동 백업, 복구 시간 목표)
   - 파일 저장소 백업

5. **배포 환경 구성**
   - 로컬 개발 → 테스트 → 스테이징 → 프로덕션
   - 각 환경의 데이터베이스/파일 저장소 분리

6. **모니터링/로깅 전략**
   - API 응답 시간 측정 (목표: < 1초)
   - 에러율 추적 (예: 5xx 에러의 자동 알림)
   - SSE/WebSocket 연결 상태 모니터링

7. **실시간 통신 구현 구체화**
   - SSE vs WebSocket 우선순위 재평가 (시나리오 4의 동시 50~100명 접속 시나리오 고려)
   - Redis pub/sub 필요 여부 (노드 서버를 여러 인스턴스로 늘릴 때)

### UI 설계 단계에서 다룰 사항

1. **Deliverables Page의 표 UI/UX**
   - 컬럼 너비 및 텍스트 오버플로우 처리
   - 정렬/필터 UI 배치 (사이드바 vs 헤더 vs 팝업)
   - 무한 스크롤 vs 페이지네이션 선택

2. **MapGen의 "파일 선택" 팝업 디자인**
   - 팝업 크기 및 검색 필터 위치
   - 행 선택 방식 (클릭 vs 라디오 버튼 vs 더블 클릭)

3. **임가공 Plan의 실시간 업데이트 사용자 피드백**
   - 다른 사용자의 변경사항이 반영될 때 시각적 표시 (toast 알림, 행 하이라이트 등)
   - 자신의 편집 중에 실시간 변경사항이 들어올 때 충돌 경고

4. **Master Page 항목 추가/삭제 팝업 디자인**
   - 인라인 입력 vs 모달 팝업
   - 중복 항목 표시 방식

5. **에러 메시지 및 경고 UI**
   - 시나리오 예외들에서 다룬 각 에러 메시지의 문구 및 토너 (심각도 표시)
   - 재시도 버튼, 상세 정보 표시 방식

### 새롭게 발견된 기술/업무 질문

1. **Status 값의 구체적 정의**
   - 현재 코드에 'new', 'checked', 'approved'로 되어 있지만, 시나리오 2에서 "의뢰 확정" 상태는 명확하지 않음
   - 실행계획 단계에서 "의뢰 확정" 상태의 정확한 이름과 그 다음 상태들을 업무 담당자와 협의 필요
   - 예: 'new' → 'checked' → 'approved' → 'requested' → 'in-progress' → 'completed'?

2. **"구분" 필드의 정의**
   - PRD 부록에서 "조립비 등 5종"이라고 하지만 정확한 항목명이 없음
   - 임가공 업무의 실제 분류 기준을 업무 담당자에게 확인 필요

3. **삭제 권한의 세부 규칙**
   - 임가공 행의 경우 "등록자 또는 MPW 관리자만 삭제"라고 했지만, Deliverables의 경우 "MPW 관리자 또는 등록자"라는 표현이 같음
   - 등록자가 자신의 행만 삭제 가능한지, 아니면 다른 사용자의 행도 삭제 가능한지 명확히 필요

4. **파일 저장 위치 및 접근 제어**
   - Deliverables의 엑셀 파일을 서버의 어느 디렉토리에 저장할지
   - 파일 접근 권한: 모든 사용자가 다운로드 가능한지, 특정 권한 필요한지

5. **SSE vs 폴링의 성능 기준**
   - 시나리오 4에서 50~100명 동시 접속에서 실시간 성능이 어느 정도 필요한지 (예: 1초 이내 반영 vs 5초 이내 충분)
   - 이에 따라 SSE/WebSocket/폴링의 선택이 달라질 수 있음
