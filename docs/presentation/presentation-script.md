# 발표 대본: Claude Code로 해 본 풀스택 바이브 코딩

- 대상 자료: `docs/presentation/mpw-plus-vibe-coding-journey.html` (발표 탭 16장 + 타임라인·요청 로그·용어 사전 탭)
- 청중: SW 개발팀. 웹 풀스택 개발자부터 웹을 처음 접하는 펌웨어 개발자까지
- 시간: **50분** = 발표 43분 + 탭 시연 2분 + 질의응답 5분
- 말투: 경험 공유. "이렇게 해야 한다"가 아니라 "이렇게 해 봤더니 이랬다"

## 읽는 법

- `⏱ 3분 · 누적 05:00`: 이 장에 쓸 시간과, 이 장이 끝났을 때의 경과 시간
- `[동작]`: 화면에서 할 일 (클릭, 탭 전환 등)
- 큰따옴표 없는 문단: 그대로 읽어도 되는 대사
- `💡 펌웨어 비유`: 웹을 모르는 분들이 많을 때 덧붙이는 설명. 시간이 부족하면 건너뜁니다.
- `⏩ 줄이기`: 시간이 밀릴 때 생략해도 되는 부분

## 시작 전 준비 (발표 10분 전)

1. HTML 파일을 Chrome으로 열고 **발표 탭 첫 장**에 둡니다. 인터넷 연결은 필요 없습니다.
2. 오른쪽 위 "테마 전환"으로 **밝은 테마**를 고릅니다. 프로젝터에서는 밝은 쪽이 잘 보입니다.
3. `Ctrl` + `+`로 글자를 125~150% 정도 키웁니다.
4. 키보드 `→` / `←`로 넘깁니다. 슬라이드 빈 곳을 클릭해도 다음 장으로 넘어갑니다.
5. 밑줄 친 용어를 클릭하면 설명 상자가 뜹니다. 질문이 나오면 그 자리에서 눌러 보여 주면 됩니다. `Esc`로 닫습니다.
6. PowerPoint 파일을 쓸 경우, 각 장의 발표자 노트에 이 대본의 요약이 들어 있습니다.

## 1장 · 표지

`⏱ 2분 · 누적 02:00`

안녕하세요. 오늘은 제가 지난 9월 중순부터 10월 초까지 약 3주 동안 해 본 "바이브 코딩" 경험을 공유하려고 합니다.

요즘 바이브 코딩이라는 말을 많이 들으실 텐데요. 회사에서도 언젠가 본격적으로 쓰게 될 것 같아서, 그 전에 제가 직접 한 번 끝까지 해 보자는 생각으로 시작했습니다.

바이브 코딩을 한 문장으로 말하면, **코드를 한 줄씩 직접 쓰는 대신, 원하는 결과를 말로 설명하고 AI가 만든 결과를 확인하면서 고쳐 나가는 개발 방식**입니다. 저는 Anthropic의 Claude Code라는 도구를 썼습니다.

[동작] 화면 아래쪽 검은 상자를 가리킵니다.

이 상자의 첫 줄이 9월 18일에 제가 처음 입력한 문장입니다. "Svelte 기반의 웹 시스템을 만들고 싶어. 채팅으로 만든 결과물을 여기서 가져올 수 있을까?" 그리고 아래 줄이 22일 뒤 마지막 결과입니다. GitHub에 PR 마흔두 번째가 합쳐졌고, 이슈 22개가 모두 닫혔고, 자동 테스트 275개가 통과하는 상태가 됐습니다.

오늘은 이 첫 줄과 마지막 줄 사이에 무슨 일이 있었는지를 시간 순서대로 말씀드리겠습니다.

## 2장 · 왜, 어떤 조건에서 했나

`⏱ 2분 · 누적 04:00`

먼저 조건부터 말씀드리겠습니다. 결과물보다 이 조건이 더 중요하다고 생각해서입니다.

[동작] 오른쪽 표를 가리킵니다.

출발점은 Claude 채팅으로 만들어 둔 요구사항 문서 하나와 화면 네 개였습니다. 이 화면들은 데이터를 브라우저 메모리에만 들고 있어서, 새로고침하면 입력한 게 다 사라지는 시제품이었습니다.

저는 프론트엔드, 즉 화면 쪽은 조금 해 봤지만 **백엔드와 데이터베이스는 경험이 전혀 없었습니다.** 그래서 처음부터 "학습 목적이니까 Claude가 제안하는 걸 따라가 보자"고 정했습니다.

목표는 실제 사내 시스템인 MPW Plus에 붙일 2차 기능을 완성해서 1차 개발자분께 넘기는 것이었습니다.

제약도 있었습니다. 회사 PC에서는 claude 사이트 접속이 막혀 있습니다. 그래서 집 PC에 Claude Code를 띄워 두고, 회사에서는 태블릿으로 그 세션에 원격으로 접속해서 지시했습니다. 화면을 제 눈으로 바로 볼 수 없는 상태로 개발한 셈입니다. 이 제약이 뒤에서 여러 번 등장합니다.

## 3장 · 풀스택 한 장 지도

`⏱ 5분 · 누적 09:00`

이 장은 웹을 처음 접하시는 분들을 위해 넣었습니다. 오늘 나오는 용어들이 전체 그림의 어디에 있는지 먼저 잡고 가겠습니다.

[동작] 왼쪽의 네 층을 위에서 아래로 짚어 가며 설명합니다.

맨 위가 **사용자**입니다. Chrome 같은 브라우저로 접속합니다.

두 번째가 **프론트엔드**, 사용자가 보는 화면입니다. 브라우저 안에서 실행됩니다. 저는 SvelteKit이라는 도구로 만들었습니다.

화면이 데이터를 저장하거나 불러오려면 서버에 요청을 보냅니다. 이때 정해진 주소와 형식이 있는데, 이것을 **API**라고 부릅니다. 주고받는 내용은 JSON이라는 텍스트 형식입니다.

세 번째가 **백엔드**, 화면 뒤에서 일하는 서버 프로그램입니다. 로그인한 사람이 누구인지, 이 사람이 이 데이터를 지워도 되는지 같은 규칙을 여기서 판단합니다. Node.js 위에서 Express라는 도구로 만들었습니다.

맨 아래가 **데이터베이스**입니다. 데이터를 오래 보관하는 곳이고 PostgreSQL을 썼습니다. 백엔드와 데이터베이스 사이에는 Knex라는 도구가 있는데, 백엔드 코드를 데이터베이스가 알아듣는 SQL 명령으로 바꿔 주는 통역 역할입니다.

> 💡 **펌웨어 비유** (웹이 처음인 분이 많으면 꼭 넣습니다)
>
> - 프론트엔드는 장비의 **HMI나 디스플레이 UI**에 가깝습니다. 사용자 입력을 받고 상태를 보여 줍니다.
> - API는 보드 사이의 **통신 프로토콜**입니다. "이 명령을 이 형식으로 보내면 이 응답이 온다"는 약속이고, 뒤에 나올 **Swagger는 그 프로토콜의 ICD, 인터페이스 명세서**라고 보시면 됩니다.
> - 백엔드는 메인 MCU에서 도는 **제어 로직**, 데이터베이스는 **플래시나 EEPROM에 저장하는 영역**입니다.
> - 데이터베이스 구조를 바꿀 때 쓰는 **마이그레이션**은, 펌웨어를 업데이트할 때 예전 버전의 저장 데이터를 새 구조로 변환하는 코드와 같은 개념입니다.

[동작] 오른쪽 아래 "식당으로 비유하면" 표를 가리킵니다.

비유가 더 편하신 분은 식당으로 생각하시면 됩니다. 프론트엔드는 손님이 보는 홀과 메뉴판, API와 Swagger는 주문서 양식과 그 작성 설명서, 백엔드는 주방, 데이터베이스는 창고입니다.

[동작] 밑줄 친 "Knex"를 클릭해 설명 상자를 한 번 보여 주고 `Esc`로 닫습니다.

발표 중에 모르는 용어가 나오면, 이렇게 밑줄 친 단어를 누르면 설명이 뜹니다. 자료를 나눠 드리니 나중에 천천히 보셔도 됩니다.

⏩ 줄이기: 시간이 밀리면 식당 비유는 생략하고 펌웨어 비유만 말합니다.

> 💡 **용어 정리** (Git을 잘 안 쓰시는 분들을 위해)

## 6장 · 1막 · 작업 환경 만들기 (9/18–9/22)

`⏱ 3분 · 누적 17:00`

여기서부터는 시간 순서대로 가겠습니다. 장마다 주황색 카드가 **제가 실제로 입력한 문장**이고, 초록색 카드가 **그 결과**입니다.

[동작] 왼쪽 주황 카드를 가리킵니다.

제일 먼저 한 일은 Claude가 일하는 규칙을 정한 것입니다. "CLAUDE.md를 한국어로 번역해 주고, 앞으로 모든 대화는 한국어로 하고, 오버엔지니어링 금지를 추가해 줘."

CLAUDE.md는 Claude Code가 작업을 시작할 때마다 **가장 먼저 읽는 규칙 파일**입니다. 사람으로 치면 업무 수칙입니다. "오버엔지니어링 금지"는 시키지 않은 기능을 미리 만들지 말라는 뜻입니다. 이 한 줄 덕분에 결과물이 끝까지 단순하게 유지됐습니다.

[동작] 오른쪽 카드를 가리킵니다.

그리고 작업이 끝나면 PC가 "작업이 완료되었습니다"라고 한국어로 말해 주게 했습니다. 이런 걸 **훅(Hook)**이라고 하는데, 특정 시점에 자동으로 실행되는 스크립트입니다. 원격으로 일하다 보니 끝났는지 알기 어려워서 만들었습니다.

[동작] 아래 회색 메모를 가리킵니다.

시행착오도 있었습니다. 첫날 원격으로 화면 캡처를 해 달라고 했다가 작업이 끝나지 않았습니다. 그때 제가 "무한 루프 아니야? 토큰이 다 소모될까 봐 걱정이네, 멈춰 줘"라고 입력했습니다. 그 뒤로는 **오래 걸리면 바로 멈추고 상황을 묻는 습관**이 생겼습니다.

## 7장 · 2막 · 설계 문서 8개 (9/23–9/29)

`⏱ 3분 · 누적 20:00`

두 번째 단계는 설계 문서입니다. 이 단계에서 가장 효과가 좋았던 방법을 소개하겠습니다.

[동작] 왼쪽 주황 카드를 가리킵니다.

문서를 만든 뒤에 이렇게 입력했습니다. "전문 서브에이전트를 이용해서, 완전성, 명확성, 추적성, 검증 가능성, 유지보수성, 이 다섯 가지 기준으로 방금 작성한 도메인 정의서를 평가해 줘."

**서브에이전트**는 특정 분야를 맡는 보조 AI입니다. 문서를 쓴 AI와 다른 관점으로 검토를 맡기는 겁니다. 결과로 항목별 점수와 빠진 내용 목록이 나옵니다.

여기서 중요한 건, 빠진 내용 중 상당수가 **업무에 관한 사실**이었다는 점입니다. 예를 들어 "임가공과 Assembly는 같은 업무인가?" 같은 것은 AI가 알 수 없습니다. 그건 제가 답해야 했습니다. 제가 답하고, 다시 평가받고, 이걸 몇 번 반복했습니다.

[동작] 오른쪽 목록을 위에서부터 짚습니다.

이렇게 9월 23일부터 29일까지 문서 8개를 만들었습니다. 업무 용어를 정리한 도메인정의서, 제품 요구사항 문서인 PRD, 사용자가 실제로 쓰는 순서를 이야기로 쓴 사용자 시나리오, 데이터베이스 표 설계도인 ERD, 할 일을 쪼갠 실행계획, 화면 뼈대인 와이어프레임까지입니다.

## 8장 · 2막 · 판단을 맡기는 법

`⏱ 3분 · 누적 23:00`

이 장은 제가 개인적으로 가장 배운 게 많았던 부분입니다.

강좌에는 "이 프롬프트를 입력하세요"라는 예시가 계속 나옵니다. 그런데 강좌의 예제 프로젝트와 제 프로젝트가 같지 않잖아요. 백엔드를 모르니 그 단계가 저한테도 필요한지 판단할 수가 없었습니다.

[동작] 주황 카드를 가리킵니다.

그래서 이렇게 물었습니다. "동영상에서는 이 예시 프롬프트를 진행하라고 하네. 내 과제에도 이 DDL 생성 과정이 필요한지 판단해 주고, 적절하다면 예시대로 작업해 줘. 필요 없다면 알려 줘. 백엔드를 잘 몰라서 내가 판단을 못 하겠어."

DDL은 데이터베이스에 표를 만드는 명령문입니다. 결과는 "필요하다"는 판단과 그 이유였고, 그다음에 파일이 만들어졌습니다.

솔직히 전부는 아닙니다. 특히 백엔드는 처음이었습니다. 대신 문서로 무엇을 만들지 먼저 합의했고, 자동 테스트 275개와 실제 화면 점검으로 동작을 확인했습니다. 코드를 한 줄씩 읽는 대신 "결과가 맞는지"를 확인하는 방식이었습니다. 실무에 쓸 때는 리뷰할 수 있는 사람이 함께 봐야 한다고 생각합니다.

**Q. AI가 만든 코드 품질은 믿을 만한가요?**
제가 느끼기에는 규칙과 기준을 얼마나 분명하게 주느냐에 따라 크게 달라졌습니다. "오버엔지니어링 금지", "테스트 커버리지 80% 이상", "이 구조를 지킬 것" 같은 규칙을 정해 두니 일관되게 지켰습니다. 그래도 점검에서 사람이 찾아낸 문제가 있었으니, 확인 단계는 꼭 필요합니다.

**Q. 시간은 얼마나 들었나요?**
달력으로는 22일입니다. 회사에서 태블릿으로 집 PC에 원격 접속해서 했기 때문에 주로 평일 낮에 작업했고, 하루에 1~2시간 정도 집중했습니다. 처음 9일은 거의 문서 작업이었고, 구현은 10월 6일부터 사흘 정도에 집중됐습니다.

**Q. 비용이나 토큰 사용량은요?**
Claude Pro 요금제로 진행했습니다. 첫날 오래 걸리는 작업 때문에 토큰 걱정을 한 적이 있어서, 그 뒤로는 막히면 바로 멈추게 했습니다. 작업 종류별 사용량을 정확히 비교해 보지는 않았습니다.

**Q. 회사 코드에도 써도 되나요? 보안은요?**
이번 작업은 회사 밖에서, 개인 PC와 개인 저장소로 한 학습용 프로젝트입니다. 회사 PC에서는 claude 접속이 막혀 있기도 합니다. 실제 회사 코드에 쓰려면 회사의 보안 정책과 승인된 도구를 따라야 한다고 생각합니다. 저도 비밀번호나 개인 정보가 저장소나 자료에 들어가지 않게 신경 썼습니다.

**Q. 펌웨어 개발에도 쓸 수 있을까요?**
문서를 먼저 만들고, 할 일을 이슈로 쪼개고, 반복 절차를 명령으로 만드는 흐름은 그대로 쓸 수 있을 것 같습니다. 다만 실제 보드에서만 확인할 수 있는 부분은 웹처럼 AI가 자동으로 확인하기 어려우니, 시험은 사람이 맡는 비율이 더 클 것 같습니다. 이건 저도 아직 해 보지 않아서 경험담이 아니라 생각임을 말씀드립니다.

**Q. 처음 시작하려면 무엇부터 하면 되나요?**
작은 것 하나로 시작하시길 권합니다. 첫 번째로 규칙 파일에 "한국어로, 오버엔지니어링 금지"를 적고, 두 번째로 만들고 싶은 것을 문서로 설명하게 한 뒤 평가를 시켜 보세요. 오늘 자료의 "자주 쓴 프롬프트 레시피" 표를 그대로 써 보셔도 됩니다.
