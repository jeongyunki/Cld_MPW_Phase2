# MPW Plus 2차 개발 PRD (Product Requirements Document)

> 작성 단계: PRD (2/6) — 다음 단계는 페르소나 정의 → ERD 설계 → 실행계획 → UI 설계 순으로 진행한다.
> 이 문서는 도메인정의서에서 정의한 범위의 구체적인 기능/비기능 요구사항, 기술 아키텍처 방향을 정한다.

---

## 1. 개요 및 목적

**MPW Plus**는 반도체 MPW(Multi Project Wafer) 관련 업무를 지원하는 웹 시스템이다. 2차 개발은 기존 1차 시스템에 MapGen Web(SF Generator 웹 전환), 임가공 Plan(외주 가공 통합), Deliverables Page(엑셀 등록) 기능을 추가하고, 이를 뒷받침할 백엔드(서버+데이터베이스)를 새로 구축하는 것을 목표로 한다.

**핵심 성공 기준**
- (기술) PC 환경에 관계없이 MapGen Web이 일관되게 동작
- (업무) 개인별 엑셀 대신 공유 플랫폼 위에서 임가공 현황 관리
- (비즈니스) 1000명 이상의 기획팀/설계팀/기술팀/제조팀/품질팀/MPW 관리자 사용자 기반 중, 동시 접속 50~100명이 입력/조회/편집 가능

---

## 2. 목표 사용자 및 사용 시나리오

### 목표 사용자 세그먼트
- **기획팀**: MPW 생산 일정 계획 및 운영, Fab Out 공지, Deliverables 정보 관리 (Fab Out 공지는 1차 시스템의 기완료 기능 — 2차 개발 범위 아님, 도메인정의서 5절 참조)
- **설계팀**: 반도체 칩 설계, MapGen Web을 통해 도면 생성, 임가공 항목 신청 등록
- **기술팀**: 반도체 칩 동작 검증
- **제조팀**: MPW 생산 진행 및 상황 추적, MapGen Web 파일에 따른 Sawing 실행
- **품질팀**: 반도체 칩 품질 검증, MapGen Web 파일 참고하여 모듈 검증
- **MPW 관리자**: MapGen Web을 통해 도면 생성, 임가공 공정별 진행 현황 조회 및 승인, 조립처와의 임가공 일정 조율

조직 규모 1000명 이상 → 동시에 50~100명이 시스템에 접속해 데이터를 조회/편집하는 상황 발생 가능

### 대표 사용 시나리오
1. **MapGen 도면 작성** — 기획팀이 엑셀 데이터를 Deliverables Page에 등록 → 설계자 또는 MPW 관리자가 MapGen Web에서 해당 파일을 선택해 즉시 도면 생성 → 품질팀과 제조팀에 MapGen Web 파일 전달
2. **임가공 진행 관리** — 설계팀의 여러 담당자가 동시에 임가공 계획을 입력 → MPW 관리자는 월별 임가공 계획을 취합하여 임가공 의뢰, 임가공 계획 리스트의 진행 상태 업데이트
3. **Master 항목 유지보수** — MPW 관리자가 조립처/PKG Type 등 dropdown 항목 추가 → 전체 사용자가 즉시 새 항목 적용

## 3. 기능 요구사항

### 3.1 Deliverables Page (신규 기능)

**목적**: 2차 프로토타입 환경에서 엑셀 파일 기반 Deliverables 정보를 등록·관리하는 화면.
(향후 1차 시스템에 병합될 때는 1차의 실제 Deliverables 데이터와 통합하는 별도 과제로 처리)

**FR-DL-01: Deliverables 등록 (Create)**
- 사용자 스토리: "기획팀으로서, 새로운 MPW 차수와 공정명을 등록하고 엑셀 파일을 업로드하고 싶다"
- 입력: MPW 차수(텍스트), 공정명(텍스트), 엑셀 파일
- 처리: 파일을 서버에 저장, DB에 메타데이터 기록 (차수+공정명+파일경로+등록일시+등록자)
- 수용 기준
  - 차수/공정명 미입력 시 "필수 입력값" 에러 표시
  - 파일 크기 제한(예: 10MB 이상이면 경고)
  - 등록 완료 시 Deliverables 목록 테이블에 새 행 추가

**FR-DL-02: Deliverables 목록 조회 (Read)**
- 사용자 스토리: "기획팀으로서, 등록된 모든 Deliverables를 표 형태로 조회하고 싶다" (설계팀/MPW 관리자도 MapGen Web 파일 선택 시 같은 목록을 조회)
- 표시 항목: 차수, 공정명, 파일명, 등록일시, 등록자
- 정렬/필터: 차수 또는 공정명으로 검색 가능
- 수용 기준
  - 서버에서 페이지네이션(한 화면 10~20건)으로 조회
  - 같은 차수+공정명이 여러 번 등록된 경우, 모두 표시 (중복 허용, "최신순" 정렬 기본값)

**FR-DL-03: Deliverables 파일 다운로드 (Read)**
- 사용자 스토리: "설계팀으로서, Deliverables 목록에서 원하는 항목의 엑셀 파일을 다운로드해 MapGen으로 작업하고 싶다"
- 처리: 표의 각 행에 "다운로드" 버튼, 클릭하면 해당 파일 다운로드
- 수용 기준
  - 실제 파일이 아닌 링크만으로 구현 가능 (MapGen이 URL 기반 파일 선택으로 확장될 때)

**FR-DL-04: Deliverables 삭제 (Delete)**
- 사용자 스토리: "MPW 관리자로서, 잘못 등록된 Deliverables를 삭제하고 싶다"
- 처리: 행 선택 후 "삭제" 버튼 클릭 → 체크박스 방식으로 다중 삭제 가능
- 수용 기준
  - 삭제 전 확인 팝업 표시
  - 삭제 시 파일도 서버에서 제거
  - (권한) MPW 관리자(Master Page 수정 권한 보유) 또는 등록자만 삭제 가능 → 다음 단계(실행계획)에서 권한 규칙 확정

### 3.2 MapGen Web (기존 기능 확장)

**목적**: PC 환경에 관계없이 웹 브라우저에서 Module/Sawing Floorplan 도면을 생성

**기존 기능 (유지)**

**FR-MG-01: 엑셀 텍스트 붙여넣기 입력**
- 사용자가 엑셀 셀 범위를 복사해 textarea에 붙여넣으면 자동 파싱 후 canvas에 도면 그리기
- 현재 구현 상태 유지 (프로토타입에서 검증됨)

**신규 기능**

**FR-MG-02: Deliverables 파일 선택 입력**
- 사용자 스토리: "설계팀으로서, Deliverables Page에 등록된 파일 목록을 팝업으로 보고 원하는 파일을 선택해 즉시 도면을 그리고 싶다" (MPW 관리자도 동일한 방식으로 사용)
- 입력: "Excel 파일 선택" 버튼 클릭 → 팝업으로 Deliverables 목록 표 표시
- 처리: 팝업에서 행(차수+공정명)을 선택하면 해당 엑셀 파일을 서버에서 다운로드해 textarea에 자동 입력 → 기존 파싱 로직 재사용
- 수용 기준
  - 팝업에 "차수", "공정명", "등록일시" 컬럼 표시 (파일 다운로드 기능과 동일한 데이터 조회)
  - 파일 선택 실패 시 에러 메시지 표시
  - textarea가 이미 데이터를 담고 있으면 "기존 데이터를 덮어쓰시겠습니까?" 확인 후 진행

### 3.3 임가공 Plan (기존 기능 확장)

**목적**: 매월 발생하는 외주 조립·가공 업무를 한 화면에서 통합 관리, 개인별 엑셀 대신 공유 데이터 제공

**기존 기능 (유지 및 개선)**

**FR-IM-01: 임가공 Plan 행 추가 (Create)**
- 사용자 스토리: "설계팀으로서, 새로운 임가공 항목을 신청하기 위해 임가공 작업을 추가하고 필수 정보(조립처, Chip size, PKG Type 등)를 dropdown에서 선택하고 싶다"
- 입력 (현재 코드 `src/lib/imgagongStore.svelte.js`, `CLAUDE.md` 기준 — Date/Status는 자동 입력이라 제외):
  - dropdown: 구분(category), 조립처(assembler), Chip size(chipSize), PKG Type(pkgType) — 옵션은 Master Page에서 관리
  - key-in: Module(module), 과제명(projectName), GCM Code(gcmCode), 고객(customer), LOT수(lotCount, 숫자), PKG 수량(pkgQty, 숫자), 과제 담당자(owner)
- 처리: 새 행을 DB에 저장, 자동으로 생성일시(date, "YYYY-MM-DD HH:MM")와 status('new')를 입력
- 수용 기준
  - dropdown 항목은 Master Page에서 추가/관리됨
  - 모든 필수 필드가 채워져야 저장 가능 (어떤 필드가 필수인지는 실행계획 단계에서 업무 담당자와 확정)
  - 등록 후 즉시 목록에 새 행 추가 (다른 사용자의 화면에도 실시간 반영)

**FR-IM-02: 임가공 Plan 목록 조회 (Read)**
- 사용자 스토리: "MPW 관리자로서, 현월/지난월의 임가공 계획을 기간별로 필터링해 조회하고 진행 현황을 파악하고 싶다" (설계팀도 자신이 등록한 항목을 같은 화면에서 조회)
- 표시 항목 (현재 코드 기준 13개 컬럼): Date, Status, 구분, 조립처, Chip size, Module, 과제명, GCM Code, PKG Type, 고객, LOT수, PKG 수량, 과제 담당자
- 필터: 조회 기간(시작 년월 ~ 종료 년월, `<input type="month">` 두 개) 선택 → `date.slice(0, 7)`을 문자열로 비교해 필터링
- 정렬: 생성일시 역순(최신순) 기본값
- 수용 기준
  - 서버에서 페이지네이션(한 화면 20~30건)으로 조회
  - 기간 선택 전 기본값은 "올해 1월 ~ 올해 12월"(현재 코드 동작 유지). "최근 N개월"로 바꿀지는 실행계획/UI 설계 단계에서 재검토 가능
  - 다른 사용자가 입력한 데이터도 실시간으로 화면에 반영됨

**FR-IM-03: 임가공 Plan 행 편집 (Update)**
- 사용자 스토리: "MPW 관리자로서, 임가공 작업의 진행 현황을 조회하고 승인하기 위해 status를 업데이트하고 싶다"
- 입력: 각 행의 Status dropdown을 변경 (현재 코드 기준 상태값: 'new', 'checked', 'approved' — Master Page에서 추가/삭제 가능하나 신규 행은 항상 'new'로 고정)
- 처리: 변경 사항을 즉시 DB에 저장
- 수용 기준
  - Date를 제외한 모든 필드(구분/조립처/Chip size/PKG Type dropdown, Module/과제명/GCM Code/고객/LOT수/PKG 수량/과제 담당자 key-in)가 표 안에서 inline으로 편집 가능 (현재 코드 동작과 동일하게 유지)
  - 편집 시 "마지막 수정일시"와 "수정자" 기록 (선택사항, 권한/감시 추적이 필요한 경우 고려)

**FR-IM-04: 임가공 Plan 행 삭제 (Delete)**
- 사용자 스토리: "설계팀으로서, 잘못 입력된 임가공 행을 삭제하고 싶다"
- 처리: 행 체크박스 선택 후 "삭제" 버튼 → 다중 선택 가능
- 수용 기준
  - 삭제 전 확인 팝업: "선택된 X개 행을 삭제하시겠습니까?"
  - 삭제 시 DB에서 실제 제거 (soft delete vs hard delete는 다음 단계에서 결정)
  - (권한) 등록자(설계팀) 또는 MPW 관리자만 삭제 가능 → 다음 단계(실행계획)에서 권한 규칙 확정

**신규 기능**

**FR-IM-05: 임가공 Plan 실시간 공유**
- 사용자 스토리: "여러 담당자가 동시에 임가공 Plan을 보면서 협업하고 싶다"
- 처리: SSE(Server-Sent Events)를 통해 다른 사용자의 입력/수정/삭제가 실시간으로 반영 (6절 참조)
- 수용 기준
  - 전체 1000명 규모(동시 접속 50~100명 수준) 환경에서 응답 시간 < 2초
  - 데이터 충돌 처리: 동일 행을 두 사용자가 동시에 편집하면, 낙관적 잠금(버전 번호 비교)으로 감지해 나중 요청에 충돌 에러를 반환한다(4.2절 참조). 구체적 구현은 다음 단계에서 확정.
  - (선택) 사용자별 cursor 위치 표시 (협업 UX 향상, 우선순위 낮음)

**FR-IM-06: 임가공 의뢰 일괄 확정**
- 사용자 스토리: "MPW 관리자로서, 설계팀이 등록한 여러 임가공 항목을 월별로 취합해서 한 번에 '의뢰' 상태로 확정하고 싶다"
- 입력: 체크박스로 여러 행 선택 → "의뢰 확정" 버튼
- 처리: 선택된 행들의 Status를 일괄로 의뢰 확정 상태로 변경 (구체적 상태값 명칭은 Master Page의 Status 목록에 추가 필요 — 현재 'new'/'checked'/'approved' 외 신규 값)
- 수용 기준
  - 확정 전 확인 팝업: "선택된 X개 항목을 의뢰 확정하시겠습니까?"
  - MPW 관리자 권한을 가진 사용자만 이 버튼을 사용할 수 있음
  - 확정 후 상태 변경이 실시간으로 전체 사용자 화면에 반영됨 (FR-IM-05와 동일한 실시간 채널 사용)
  - 확정 이후에도 상태를 되돌릴 수 있는지(예: '의뢰 취소') 여부는 다음 단계(실행계획)에서 업무 담당자와 확정 필요

### 3.4 Master Page (기존 기능 유지)

**목적**: 임가공 Plan과 Deliverables Page에서 사용하는 dropdown 항목(Status, 구분, 조립처, Chip size, PKG Type)을 중앙에서 관리

**FR-MS-01: Master 항목 추가 (Create)**
- 사용자 스토리: "MPW 관리자로서, 새로운 조립처 또는 PKG Type을 Master에 추가하고 전체 사용자에게 즉시 반영하고 싶다"
- 입력: 필드명(Status/구분/조립처/Chip size/PKG Type), 항목명
- 처리: 새 항목을 DB에 저장
- 수용 기준
  - 각 필드마다 별도 섹션으로 표시 (현재 4개 필드)
  - 추가 후 즉시 다른 사용자의 dropdown에도 반영

**FR-MS-02: Master 항목 조회 (Read)**
- 현재 등록된 모든 Master 항목을 필드별로 표 또는 목록 형태로 표시

**FR-MS-03: Master 항목 삭제 (Delete)**
- 사용자 스토리: "MPW 관리자로서, 사용하지 않는 조립처를 Master에서 제거하고 싶다"
- 처리: 항목 선택 후 삭제 버튼
- 수용 기준
  - 삭제 전 확인: "이 항목을 사용 중인 행이 X개 있습니다. 계속 삭제하시겠습니까?"
  - (선택) 삭제 불가 옵션: 사용 중인 항목은 삭제 불가로 처리 (다음 단계 결정)

**특수 규칙**: Status 필드는 Master Page에서 편집 가능하지만, 새로운 임가공 행 추가 시 Status는 항상 'new'로 고정 (기존 프로토타입 동작 유지)

### 3.5 백엔드 API (신규 구축)

**목적**: 프론트엔드의 모든 데이터 CRUD 작업을 지원하고, 다중 사용자 동시 접속 환경에서 데이터 정합성 보장

**데이터 모델** (상세 스키마는 ERD 단계에서 설계)
- `deliverables`: 차수, 공정명, 파일경로, 등록일시, 등록자, ...
- `imgagong_plan`: 생성일시(date), Status, 구분(category), 조립처(assembler), Chip size(chipSize), Module(module), 과제명(projectName), GCM Code(gcmCode), PKG Type(pkgType), 고객(customer), LOT수(lotCount), PKG 수량(pkgQty), 과제 담당자(owner), 수정일시, 수정자, ... (필드명은 현재 코드 `imgagongStore.svelte.js` 기준, 상세 타입/제약은 ERD 단계에서 확정)
- `master_items`: 필드명, 항목명, 순서, ...
- `users`: 이름, 이메일, 권한, 가입일, ... (인증 방식 확정 후 설계)

**API 엔드포인트** (RESTful, 6절 참조)
- `GET /api/deliverables` — 목록 조회 (페이지네이션, 검색 필터 포함)
- `POST /api/deliverables` — 항목 등록 (파일 업로드 포함)
- `DELETE /api/deliverables/{id}` — 항목 삭제
- `GET /api/imgagong-plans` — 목록 조회 (기간 필터, 페이지네이션)
- `POST /api/imgagong-plans` — 행 추가
- `PATCH /api/imgagong-plans/{id}` — 행 편집
- `DELETE /api/imgagong-plans/{id}` — 행 삭제
- `GET /api/master-items` — 전체 Master 항목 조회 (필드별)
- `POST /api/master-items` — 항목 추가
- `DELETE /api/master-items/{id}` — 항목 삭제
- (SSE) `GET /api/imgagong-plans/stream` — 실시간 임가공 데이터 업데이트 구독 (선택, 6절 참조)

**비기능 요구사항** (자세한 내용은 4절)
- 응답 시간: API 호출 < 1초, 리스트 조회 < 2초
- 동시성: 전체 1000명 규모(동시 접속 50~100명 수준) 환경에서 안정적 운영
- 트랜잭션: 낙관적 잠금 기반 충돌 감지(4.2절 참조), 구체적 구현은 다음 단계에서 확정

## 4. 비기능 요구사항

### 4.1 성능 및 확장성
- **응답 시간**: 단일 API 호출 < 1초, 리스트 조회 < 2초 (네트워크 지연 제외)
- **동시 사용자**: 전체 사용자 1000명 이상, 동시 접속 최대 50~100명 지원 (데이터 정합성 손상 없음)
- **데이터 규모**: 초기 100~1000건 수준의 Deliverables/임가공 행 처리 가능 (향후 성장에 대비해 페이지네이션/인덱싱 설계)
- **파일 업로드**: Deliverables에 등록되는 엑셀 파일 크기 최대 10MB (다운로드 포함 처리 시간 < 3초)

### 4.2 데이터 정합성 및 동시성 제어
- **문제**: 여러 사용자가 동시에 같은 임가공 행을 편집할 때 발생하는 데이터 충돌
- **권장 방식** (다음 단계 확정): **낙관적 잠금** (Optimistic Locking)
  - 각 행에 버전 번호(version) 추가
  - 편집 시 "버전 X인 상태에서 변경"으로 저장 요청
  - 버전이 맞지 않으면 "다른 사용자가 먼저 수정했습니다" 에러 표시 → 사용자가 새로고침 후 재시도
  - **근거**: 초보자 친화적 구현, 일반적인 사내 도구 규모에서 충돌 빈도 낮음
- **대안** (고려만): 비관적 잠금 (행 선택 시 잠금, 수정 완료 시 해제) — 구현 복잡도 높고 UX 악화 가능성

### 4.3 보안
- **전제**: 사내망 폐쇄 환경 (공인 IP 미지원 가정)
- **인증**: 다음 5절 참조
- **권한**: 모든 API 엔드포인트에서 사용자 권한 확인 (삭제 권한, Master Page 수정 권한 등)
- **데이터 암호화**: 파일 업로드 시 HTTPS 사용, 저장된 파일 암호화 (선택사항, 다음 단계 결정)
- **감시/감사**: Master Page 또는 관리 대시보드에서 주요 작업 기록 조회 (구현 순서 후순위)

### 4.4 가용성 및 장애 대응
- **백업**: 데이터베이스 일일 자동 백업 (운영 정책으로 처리, 구현 세부사항은 배포/인프라 단계)

## 5. 인증/권한

### 결정 사항 (도메인정의서 8절 미해결 사항 — 해소)
"자체 구현 vs 1차 시스템의 기존 체계 재사용" 중 하나를 먼저 고르는 대신, **순서를 정했다**: 자체 구현을 1단계 목표로 먼저 완성해 동작하는 결과물을 만들고, 이후 1차 개발자와 협의가 이뤄지면 1차 시스템 인증으로 교체(전환)한다.

**이 순서를 택한 이유**
- 사용자가 백엔드/DB 개발 경험이 없어 학습 목적으로 직접 완성해보는 것이 이번 2차 개발의 목표 중 하나다(도메인정의서 8절).
- 1차 개발자와의 협의 일정이 2차 개발 착수 시점에 확정되어 있지 않다 — 협의를 기다렸다가 시작하면 그동안 아무것도 완성하지 못한다.
- 인증 로직을 처음부터 별도 모듈로 격리해두면(아래 참조), 나중에 1차 연동으로 바꾸는 비용이 작아 "일단 자체 구현으로 시작"하는 리스크가 낮다.

### 1단계 (지금 구현): 자체 구현
- Node.js + Passport.js(Local Strategy)로 이메일+비밀번호 기반 세션 인증
- `users` 테이블이 인증 자격증명(비밀번호 해시)까지 직접 보유한다(ERD `docs/6-erd.md` 참조)
- 회원가입 화면은 만들지 않는다(요청받지 않은 범위) — 초기 사용자 등록은 MPW 관리자가 Master Page 또는 별도 관리 기능으로 수동 등록
- 권한: "Master Page 수정" = `users.role`이 관리자인 사용자(= 2차의 "MPW 관리자")
  - Deliverables/임가공 행 삭제 권한도 동일 룰 적용 (세분화는 다음 단계 결정)

### 2단계 (향후, 1차 개발자 협의 후): 1차 시스템 인증으로 전환
- 목표: 2차 백엔드가 1차 사용자/권한 정보를 재사용(읽기 전용)하도록 바꿔, 사용자가 별도 계정 없이 동일 계정으로 접근
- 전환을 쉽게 하기 위해, 인증 로직은 1단계부터 별도 모듈(`middleware/auth.js`, `4-project-structure-principles.md` 참조)로 격리해서 구현한다 — 전환 시 이 모듈만 교체하면 나머지 controller/service 코드는 손대지 않는다
- 전환 시점의 기존 `users` 데이터를 1차 데이터와 어떻게 매핑할지는 전환 시점에 별도로 정한다(지금 설계하지 않음)

**최종 결정**: 1단계(자체 구현)를 지금 진행한다. 2단계 전환 시점과 방식은 1차 시스템 개발자와의 협의 결과에 따른다(9절 미해결 사항 참조).

## 6. 기술 스택 및 아키텍처 개요

### 고정된 기술 스택
- **프론트엔드**: Svelte 5, SvelteKit (기존 코드베이스와 동일)
- **백엔드**: Node.js
- **데이터베이스**: PostgreSQL

### 권장 추가 기술 선택

#### 백엔드 프레임워크: **Express.js + middleware 조합**
**근거**
- Node.js 초보자도 이해하기 쉬운 미니멀한 구조
- 라우팅, 요청/응답 처리가 직관적
- 많은 튜토리얼 및 커뮤니티 자료
- 전체 1000명, 동시 접속 50~100명 규모에서도 충분한 성능 (아래 "규모 재검토" 참조)

**대안** (고려 후 제외)
- NestJS: 매우 강력하지만 학습 곡선 가파름, 과도한 abstraction
- Fastify: 성능 우수하나 Express만큼 예시 자료 많지 않음

#### ORM/데이터 접근: **Sequelize 또는 Knex.js**
**권장**: Knex.js (Query Builder)
**근거**
- 순수 SQL을 작성하되, 자동 escaping + 메서드 체인으로 가독성 향상
- 마이그레이션 도구 내장 (데이터베이스 스키마 버전 관리 용이)
- ORM(Sequelize)보다 학습 복잡도 낮음
- 초보자가 SQL을 이해하면서도 injection 공격 방지 가능

**대안** (고려 후 제외)
- TypeORM: TypeScript 전제, Express 조합 시 보일러플레이트 많음
- Prisma: 최신이지만 문서 진화 중, 사내 환경에서 문제 발생 시 지원 받기 어려울 가능성

#### API 스타일: **RESTful (JSON)**
**근거**
- GraphQL은 초보자 진입장벽 높음
- RESTful은 HTTP 메서드(GET/POST/PATCH/DELETE)와 직관적 매칭
- 현재 프론트엔드 프로토타입도 RESTful 상정

#### 실시간 통신 (선택): **Server-Sent Events (SSE) 또는 WebSocket**
**권장**: SSE (초기 단계)
**근거**
- WebSocket보다 구현 간단 (클라이언트도 EventSource API로 충분)
- 임가공 Plan의 "실시간 공유"는 SSE 단방향(서버→클라이언트)으로 충분
- 비용 및 유지보수 낮음

**점진적 확장**: 필요 시 WebSocket으로 전환 가능 (Socket.io 라이브러리)

#### 파일 저장소: **로컬 파일시스템 (초기) → S3/클라우드 (선택사항)**
**초기**: 서버 로컬 디렉토리(`/uploads` 등)에 저장
**근거**
- 사내망 폐쇄 환경, 초기 규모 작음
- 구현 복잡도 최소

**향후 (선택사항)**: AWS S3/MinIO 등으로 전환 (확장성 및 백업 용이)

### 규모 재검토 (전체 1000명, 동시 접속 50~100명 기준)

초기 권장안 작성 시 규모를 100명/동시 5~20명으로 가정했으나, 이후 1000명/동시 50~100명으로 상향됐다. 아래는 이 규모를 반영한 재검토 결과다.

- **Express.js는 그대로 유지 가능**: 동시 접속 50~100명은 대부분 짧은 CRUD 요청(응답 후 연결 종료)이라, Node.js 단일 프로세스의 이벤트 루프로 충분히 처리 가능한 수준이다. 프레임워크 교체는 불필요하다.
- **PostgreSQL 연결 풀(connection pool) 설정이 중요해짐**: 동시 사용자 50~100명이 전부 동시에 DB 쿼리를 실행하는 건 아니지만(대부분은 화면을 보고 있는 상태), 순간적으로 몰리는 상황에 대비해 Knex.js의 pool 설정(예: `min: 2, max: 10~20`)을 명시적으로 튜닝해야 한다. 이 값은 실행계획 단계에서 실측 후 조정.
- **SSE 실시간 브로드캐스트의 확장 한계**: SSE는 Node 프로세스 하나가 열린 커넥션들을 메모리에서 직접 관리하는 방식이라, 서버를 1대(단일 프로세스)로 운영하는 동안은 문제없다. 다만 나중에 안정성/부하 대비로 Node 프로세스를 여러 개(클러스터/멀티 인스턴스)로 늘리게 되면, 한 인스턴스에 연결된 사용자가 다른 인스턴스에서 발생한 변경사항을 못 받는 문제가 생긴다 — 이 경우 Redis pub/sub 같은 브로커로 인스턴스 간 메시지를 공유해야 한다.
- **권장 방향**: 지금 단계(학습 목적, 이 규모)에서는 **Node 단일 프로세스 + SSE**로 시작하고, 실행계획 단계에서 실제 부하 테스트 결과를 보고 "멀티 인스턴스 + Redis pub/sub"으로 갈지 여부를 결정한다. 처음부터 멀티 인스턴스 구조를 만드는 것은 이 프로젝트의 학습 목적과 현재 규모에 비해 과한 복잡도다.

### 아키텍처 개요

```
┌─────────────────────┐
│  클라이언트 (Svelte) │
│  - MapGen, 임가공 Plan
└──────────────┬──────┘
               │ HTTPS (SSE/REST)
               ↓
┌─────────────────────────────────────┐
│  Express 백엔드 (Node.js)            │
│  ├─ /api/deliverables               │
│  ├─ /api/imgagong-plans             │
│  ├─ /api/master-items               │
│  └─ /uploads (파일 서빙)             │
└──────────────┬──────────────────────┘
               │
       ┌───────┴────────┐
       ↓                ↓
┌──────────────┐  ┌──────────────┐
│ PostgreSQL   │  │ 파일시스템   │
│ (메인 DB)    │  │ (/uploads)   │
└──────────────┘  └──────────────┘
```

**데이터 흐름**
1. 사용자가 Deliverables 등록 (차수, 공정명, 엑셀 파일)
2. 프론트엔드가 `POST /api/deliverables`로 요청 (multipart/form-data)
3. Express가 파일을 `/uploads/deliverables/{id}.xlsx` 저장, DB에 메타데이터 기록
4. 임가공 Plan에서 사용자가 "Deliverables 선택" 클릭 → `GET /api/deliverables` 호출
5. 팝업에서 항목 선택 → `GET /uploads/deliverables/{id}.xlsx` 다운로드 후 MapGen 로직 실행

**보안 고려**
- 파일 다운로드 시 URL 직접 노출 금지, `/api/deliverables/{id}/download` 엔드포인트로 리다이렉트
- 권한 확인 후 제공 (예: 임가공 Plan 접근 권한 있는 사용자만)

## 7. 범위 (In-scope / Out-of-scope)

### In-scope (2차 개발에 포함)
- MapGen Web: 엑셀 붙여넣기 + Deliverables 파일 선택 입력 두 가지 방식
- 임가공 Plan: CRUD + 기간 필터 + 실시간 공유 기반
- Deliverables Page: 엑셀 업로드 기반 등록/조회/삭제
- Master Page: 기존 유지 + 백엔드 연동
- 백엔드 구축: Express + PostgreSQL + 파일 저장소

### Out-of-scope (제외, 도메인정의서 재확인)
- 결재 시스템 연동 ("품의상신" 버튼 삭제)
- 재무 시스템 연동 ("예산정보" 버튼 삭제)
- Assembly Workflow와 임가공 Plan의 연동 (독립적 기능)
- 1차 시스템의 Deliverables 실제 데이터와 2차 프로토타입의 통합 (별도 과제)
- 고급 보고서/대시보드 (주요 KPI 그래프, 미래 기능)
- 모바일 앱 (웹 전용)
- 다국어 지원 (한국어 기본)

### 향후 고려 사항 (2차 이후)
- 감시/감사 로그 (주요 작업 기록, 이전 버전 복원 등)
- 고급 필터/검색 (전문 검색 문법, 저장된 검색 등)
- 일괄 작업 (엑셀 업로드로 일괄 임가공 행 등록 등)
- 메일 알림 (임가공 기일 임박 시 자동 메일)

## 8. 우선순위 및 단계별 릴리즈 계획

### 단계별 릴리즈 전략

**Phase 1: 백엔드 기반 (필수, 약 2-3주)**
- PostgreSQL + Express 기본 구조 구축
- 인증 자체 구현 (Passport.js + 세션, `users` 테이블 포함 — 5절 1단계 참조, 향후 1차 인증 전환을 고려해 모듈로 분리)
- `/api/master-items` CRUD 구현
- `/api/deliverables` CRUD 구현
- 파일 업로드/다운로드 기능

**근거**: 모든 페이지가 의존하는 기초. 먼저 구축해야 다른 기능들이 백엔드에 연결 가능.

---

**Phase 2: Deliverables Page + MapGen 연동 (P0, 약 1-2주)**
- Deliverables Page 프론트엔드 구현 (목록 조회, 추가, 삭제)
- MapGen Web의 "파일 선택" 입력 방식 추가 (기존 붙여넣기 유지)
- 프론트엔드 ↔ 백엔드 완전 통합

**근거**: 2차 신규 기능의 핵심. MapGen이 파일 선택 방식으로 확장되면서 실용성 대폭 향상.

---

**Phase 3: 임가공 Plan 백엔드 연동 (P0, 약 1-2주)**
- `/api/imgagong-plans` CRUD 구현
- 프론트엔드 기존 프로토타입과 백엔드 연결
- 기간 필터 기능 확인
- 실시간 공유 기초 (SSE, 6절 참조)
- 임가공 의뢰 일괄 확정(FR-IM-06) 구현

**근거**: 비즈니스 가치 높음(임가공 통합 업무 효율화). Phase 1/2와 병렬 진행 가능.

---

**Phase 4: 실시간 협업 고도화 (P1, 약 1주)**
- SSE 안정화(재연결 처리 등). 부하 테스트 결과에 따라 WebSocket 전환 필요성 재검토(6절 참조)
- 동시성 제어 테스트 (낙관적 잠금)
- 1000명 규모(동시 접속 50~100명) 부하 테스트

**근거**: 비기능 요구사항 충족. Phase 3 후 안정화 단계.

---

**Phase 5: 통합 테스트 + 운영 준비 (P1, 약 1주)**
- 전체 기능 통합 테스트
- 도움말/설명서 작성
- 성능 최적화 (쿼리 인덱싱, 프론트엔드 로딩 최적화)
- 운영 매뉴얼 (백업, 모니터링)

**근거**: 프로덕션 배포 전 준비 완료.

## 9. 남은 미해결 사항 (다음 단계로 넘김)

### 페르소나 정의 단계에서 다룰 사항
- 각 사용자 그룹(기획팀, 설계팀, 기술팀, 제조팀, 품질팀, MPW 관리자)의 구체적 페르소나 작성
- 각 페르소나의 MapGen/임가공 Plan 사용 패턴 상세화
- Master Page 접근 권한: "MPW 관리자"가 실제로 몇 명이고 어떤 조직 소속인지 구체적 정의 필요 (Master Page 수정 권한 = MPW 관리자로 통일하기로 결정됨, 5절 참조)

### ERD 설계 단계에서 다룰 사항
- 정확한 테이블 스키마 설계
- 권한 테이블 구조 (Role-Based Access Control, RBAC)
- 파일 메타데이터 테이블 (파일명, 크기, 해시값 등)
- 감시/감사 로그 테이블 (선택사항, 향후 필요 시)
- 인덱싱 전략 (조회 성능 최적화)

### 실행계획 단계에서 다룰 사항
- 구체적 API 엔드포인트 상세 정의 (요청/응답 스키마)
- 1차 시스템 인증으로의 전환 시점과 구체적 연동 방식 (5절 2단계 참조, 1차 개발자 협의 필요)
- 데이터 충돌 처리 구현 세부사항 (낙관적 잠금 vs 비관적 잠금)
- 백업 및 재해복구 전략
- 배포 환경 구성 (로컬 개발 → 테스트 → 스테이징 → 프로덕션)
- 모니터링/로깅 전략 (응답 시간, 에러율 등)

### UI 설계 단계에서 다룰 사항
- Deliverables Page의 표 UI/UX (컬럼 너비, 소팅, 무한 스크롤 vs 페이지네이션)
- MapGen의 "파일 선택" 팝업 디자인
- 임가공 Plan의 실시간 업데이트 시 사용자 피드백 표시 (toast, badge 등)
- Master Page 항목 추가/삭제 팝업 디자인

### 구체적 기술 선택 미정 사항 (차기 회의 시 협의)
- 1차 시스템 인증 전환 가능성 여부 확인 (1차 개발자 협의, 5절 2단계 참조)
- 데이터베이스 마이그레이션 도구 선택 (Knex migrations vs Flyway vs Liquibase)
- 파일 저장소: 로컬 vs S3 vs MinIO 최종 결정
- 실시간 통신: SSE vs WebSocket vs 폴링 우선순위 재평가 (성능 테스트 후)
